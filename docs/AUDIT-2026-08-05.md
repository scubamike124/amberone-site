## Fixed

### The login endpoint told you whether an address had an account

`POST /api/auth/login` returns the same "Invalid email or password" whether or
not the address exists — but an unknown address returned *immediately*, while a
known one paid for a PBKDF2 derivation first. The reply was identical and the
timing was not, so the endpoint could be timed to enumerate accounts. An unknown
address now hashes against a fixed decoy salt, spending the same work.

### Password hashes were compared with `!==`

`===`/`!==` short-circuits at the first differing character, so the comparison
time leaked how much of the hash matched. Narrow — an attacker must guess the
stored hash, not the password — but there is no reason for a credential check to
be data-dependent. Replaced with a constant-time `timingSafeEqual` in `_lib/core.js`.

### Four endpoints returned raw internal errors to the caller

`login`, `signup`, `forgot-password` and `talk` each returned
`detail: err.message` (and signup also `err.name`) in their 500 bodies. Three of
those four are unauthenticated. Anyone able to trigger an exception got the
underlying D1 error text — table and column names, constraint names, sometimes
the failing statement; on `talk`, upstream provider errors that can echo parts
of the prompt. All four now log server-side and return only the generic message.
`forgot-password` is the sharpest case: it is deliberately vague about whether
an address exists, and the leak undid that care the moment anything threw.

## Verified sound — no change needed

- **Stripe webhook** (`functions/api/webhook.js`) — signature verified before any
  write; timestamp tolerance of 300s so a captured payload cannot be replayed
  later; length check then constant-time compare; idempotent on `event.id` via a
  `billing_events` lookup, so Stripe's retries cannot double-apply.
- **Sessions** — 32 random bytes, stored only as a SHA-256 hash, 30-day expiry
  enforced in the lookup query; cookie is `HttpOnly`, `SameSite=Lax`, and

## Pending decision — password hashing cost

`PBKDF2_ITERATIONS = 10_000`, with the comment *"kept modest for Cloudflare Pages
Functions CPU limits"*. Current guidance for PBKDF2-HMAC-SHA256 is ~600,000, so
this is roughly 60× weaker than standard: if the users table leaks, weak
passwords fall ~60× faster than they should.

**I did not change it,** because both ways of changing it blind are destructive:

- Raising the constant alone invalidates every stored hash — every existing user
  is locked out permanently, with no way back.
- Raising it *with* a migration is the correct fix, but the whole reason the
  value is low is a CPU ceiling I cannot measure from here. If the deployment is
  on a plan whose CPU limit 210k+ iterations exceeds, login stops working for
  everyone.

**The migration, when you want it:**

1. `ALTER TABLE users ADD COLUMN password_iterations INTEGER NOT NULL DEFAULT 10000`
   in `ensureSchema`.
2. `hashPassword(password, saltHex, iterations = PBKDF2_ITERATIONS)`.
3. Login verifies with `user.password_iterations`; on success, if that is below
   the current target, re-derive at the target and update the row in the same
   request. Users upgrade silently as they sign in, and nobody is locked out.
4. Signup and password-reset use the new target immediately.
5. Before shipping, measure one derivation at the candidate count against the
   real Pages plan and confirm it fits the CPU budget with headroom.

**What I need from you:** confirmation of the plan's CPU limit, or agreement to
ship the migration at a measured-safe count.

## Open

- **No rate limiting on `/api/auth/login`.** Nothing throttles password guessing.
  A D1-backed attempt counter keyed on email and IP is the natural fit here, but
  it is a feature rather than a repair, and it interacts with the decision above.
- **`ensureSchema` failures are swallowed** in `_middleware.js` with a comment
  saying handlers will surface DB errors. They now surface as generic 500s —
  which is correct for the caller, but means a schema problem is only visible in
  logs. Worth a health-check assertion.
